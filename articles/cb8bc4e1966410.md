Cloudflare Agents SDKでは、AgentがCloudflare Durable Objects（以下DO）上で動作します。DOはメモリとSQLiteストレージを持つステートフルな実行環境です。アイドル時には条件に応じてメモリからアンロードされ、コードのデプロイや基盤側の再起動によっても処理が中断される場合があります。^[アイドル時の状態遷移とデプロイ・ランタイム更新時の停止動作が説明されています [Lifecycle of a Durable Object](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)]

このような処理の中断に対して、処理の継続や状態の回復を制御する仕組みとして提供されているのがFiberです。^[Agentの処理をDurable Object上で実行し状態を永続化するFiberの仕様が説明されています [Durable execution with fibers](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/)]

この記事では、DOにおける処理の中断要因、中断を抑止するkeepAlive、状態を記録して回復するrunFiberおよびstartFiberの仕組み、チャットエージェントにおける利用例について整理します。

## Fiberとは

Cloudflare Agents SDKにおけるFiberは、DO上で実行される処理の中断に対応し、途中状態の記録や再開可能な処理を定義・制御するための仕組みです。

Fiber自体が新しいインフラストラクチャや実行ランタイムを提供するわけではありません。DOが標準で提供しているSQLiteストレージやAlarmといった既存のプリミティブを基盤とした抽象レイヤーです。^[FiberがDurable ObjectsのストレージとAlarmを基盤にして構築されていることが説明されています [Durable execution with fibers](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/)]

このFiberでは、SQLiteに保存したスナップショットをもとに回復処理へ制御を引き継ぎます。実行中の関数のクロージャや呼び出しスタックを保存して、そのまま復元する仕組みではありません。^[元のコールバックは失われ、回復フックで再開手順を実装することが説明されています [Recovery](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#recovery)]

## DOの処理の中断が起きる要因

Cloudflare Agents SDKのAgentはDOを基盤としています。DOは常時稼働し続ける仮想マシンではなく、リクエストを処理していない期間はリソース効率化のために停止します。また、インフラストラクチャの保守や設定変更によっても停止が発生します。

公式ドキュメントでは、DOのeviction（アンロードや停止）が発生する主な要因として以下の3点が挙げられています。^[evictionが発生する3つの主な要因が説明されています [Why fibers exist](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#why-fibers-exist)]

- 非アクティブタイムアウト（Inactivity timeout）によって停止します。Fiberのドキュメントでは、受信リクエストや開いているWebSocket接続がない場合の目安を約70〜140秒としています。外部のLLM APIへの通常の`fetch()`は、応答をストリーミング中でもDOを維持しません。^[通常のfetchと、DOを維持する外向きTCP・WebSocket接続の違いが説明されています [Lifecycle of a Durable Object](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)]
- Cloudflare側のランタイム更新やアプリケーションコードの再デプロイなどによって停止します。発生タイミングは非決定的です。
- DOのAlarmハンドラによる処理の実行時間が15分に達すると、Alarmハンドラのタイムアウト（Alarm handler timeout）により停止します。

メモリ上の変数、タイマー、実行中の外部APIへのHTTP接続は、eviction後の新しいインスタンスに復元されません。SQLiteに永続化したデータは残ります。^[永続化されるデータと失われる実行中の状態が区別されています [Long-running agents](https://developers.cloudflare.com/agents/concepts/agentic-patterns/long-running-agents/)]

なお、Hibernation APIで受け付けたWebSocketは、DOがhibernationしている間も接続を維持できます。WebSocket接続の存在だけで、すべてのDOが常時稼働するわけではありません。^[hibernation中のクライアント接続の維持が説明されています [Lifecycle of a Durable Object](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)]

これらの要因に対して、Fiberは以下の2つのアプローチを提供します。

- keepAliveを呼び出してハートビートを送信し、非アクティブタイムアウトによるevictionを防ぎます。
- runFiberまたはstartFiberを使用して処理の途中状態をSQLiteに保存し、evictionが発生した場合でも回復処理を呼び出して再開できるようにします。

## keepAliveによる中断の防止

keepAliveは、非アクティブタイムアウトによるDOの停止を防ぐためのAPIです。^[30秒間隔のheartbeatで非アクティブタイムアウトを防ぐkeepAliveの仕様が説明されています [keepAlive](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#keepalive)]

### 基本的な使い方

非同期処理の実行前に`this.keepAlive()`を呼び出してdisposer関数を取得し、処理の完了後に呼び出します。

```ts:src/agent.ts
const dispose = await this.keepAlive();
try {
  await longWork();
} finally {
  dispose();
}
```

一定の関数スコープ内でのみ有効化したい場合は、ヘルパーメソッドである`keepAliveWhile`を利用することも可能です。

```ts:src/agent.ts
await this.keepAliveWhile(async () => {
  await longWork();
});
```

### 内部動作と注意点

`keepAlive()`を実行すると、内部でDOのAlarmを利用して、デフォルトで30秒間隔のheartbeatを生成します。間隔は`keepAliveIntervalMs`で変更できます。すべてのdisposerが呼ばれるとheartbeatが停止します。^[設定可能な間隔と参照カウントによるheartbeatの維持が説明されています [keepAlive](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#keepalive)]

Alarmは、指定時刻にDOの`alarm()`ハンドラを呼ぶ機能です。各DOが同時に設定できるAlarmは1つで、Agents SDKはこのAlarmをスケジュールとheartbeatで共有します。SDK利用中に独自の`setAlarm()`で上書きすると、SDKが設定した次回の起動時刻も置き換わります。^[既存AlarmへのsetAlarmが時刻を上書きすることが説明されています [Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)]^[SDKがスケジュールとheartbeatを単一のAlarmで多重化することが説明されています [How it works](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#how-it-works)]

ただし、keepAliveで防ぐことができるのは非アクティブタイムアウトのみです。コードの再デプロイ、ランタイムの再起動、Alarmハンドラの15分タイムアウトなどによる中断を防ぐことはできません。また、evictionが発生した場合の回復機構も備えていません。そのため、途中状態の保持や中断後の復旧が必要な処理には、runFiberやstartFiberを使用します。

## runFiberによる状態記録と復旧

runFiberは、処理の進行状況をチェックポイントとしてSQLiteに保存しながら実行し、evictionが発生した際に回復フックを呼び出すAPIです。^[runFiberの実行モデルとチェックポイント保存の仕様が説明されています [Durable execution with fibers](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/)]

### 基本的な実装例

runFiberと回復用フックである`onFiberRecovered`を実装したAgentの抜粋です。`expensiveOperation()`と`anotherExpensiveOperation()`はアプリケーション側で定義する処理で、ここでは実装を省略しています。

```ts:src/agent.ts
import { Agent } from "agents";
import type { FiberRecoveryContext } from "agents";

export class ResearchAgent extends Agent {
  async doWork() {
    await this.runFiber("my-task", async (ctx) => {
      const step1 = await expensiveOperation();
      ctx.stash({ step1 });

      const step2 = await anotherExpensiveOperation(step1);
      this.setState({ ...this.state, result: step2 });
    });
  }

  async onFiberRecovered(ctx: FiberRecoveryContext) {
    if (ctx.name !== "my-task") return;

    const snapshot = ctx.snapshot as { step1: unknown } | null;
    if (snapshot) {
      const step2 = await anotherExpensiveOperation(snapshot.step1);
      this.setState({ ...this.state, result: step2 });
    }
  }
}
```

この例では、`step1`を保存済みの場合に`step2`を実行します。最初の`stash()`より前に中断した場合は`snapshot`が`null`となり、回復フックは何もせず終了します。また、`step2`の完了後、Fiberの回復用レコードが削除される前に中断すると、回復時に`step2`を再実行する場合があります。実際の処理では、初期入力の永続化や外部APIの冪等性キーなどを使って、この場合の回復手順も定義します。^[stash未実行時のsnapshotはnullであり、回復方針はアプリケーションが実装することが説明されています [Recovery](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#recovery)]

### 実行ライフサイクル

runFiberを実行したときの内部フローは以下の通りです。^[正常終了と例外発生時のレコード削除、keepAliveの解放が説明されています [Lifecycle](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#lifecycle)]

1. 実行開始時に、Fiber名やメタデータを含む回復用レコードがDOの専用SQLiteストレージに保存されます。
2. 内部でkeepAliveが呼び出され、処理中の非アクティブタイムアウトが防止されます。
3. 指定したコールバック関数が実行されます。
4. コールバック関数が正常終了すると、SQLite内の回復用レコードが削除され、戻り値が呼び出し元に返されます。
5. コールバック関数が例外を投げた場合も回復用レコードは削除され、エラーが呼び出し元へ送出されます。通常の例外に対する自動リトライは行われません。

正常終了・例外のいずれでも、内部で取得したkeepAliveの参照は解放されます。

### ctx.stashによるチェックポイント保存

コールバック関数に渡される`ctx`オブジェクトには、状態を保存するための`ctx.stash()`メソッドが含まれます。^[stashメソッドによる同期書き込みとスナップショットの挙動が説明されています [Checkpoints with stash](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#checkpoints-with-stash)]

- `ctx.stash(data)`に渡すデータは、JSONシリアライズ可能である必要があります。
- 書き込みはSQLiteに対して同期的に行われます。呼び出しが完了した時点でストレージへ反映されるため、直後にevictionが発生してもスナップショットは保持されます。
- `ctx.stash()`は前回保存されたスナップショットとの差分マージを行わず、スナップショット全体を上書きします。回復に必要な情報は毎回すべて含めて保存します。

### onFiberRecoveredによる回復処理

処理の途中でevictionが発生した場合、メモリ上の関数実行コンテキストや未完了のコールバックは失われます。しかし、SQLiteに未完了のFiberレコードが残ります。^[未完了のFiberが検知され回復フックが呼び出される仕組みが説明されています [Recovery](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#recovery)]

次回のDO起動時（外部からのリクエスト受信、または永続化されたAlarmの発火時）に未完了レコードが検出され、Agentクラスの`onFiberRecovered(ctx)`が呼び出されます。

- 元のコールバック関数を自動で再実行（リプレイ）する仕組みではありません。関数のクロージャ自体はシリアライズできないため、回復フック内でアプリケーション側が復旧手順を実装します。
- `ctx.name`で処理を判別し、`ctx.snapshot`に残されたデータをもとに、未完了ステップの再開や最初からの再実行、外部サービスの補償処理などを実行します。
- `runFiber()`の回復用レコードは、`onFiberRecovered()`が正常終了すると削除されます。フック内で`runFiber()`を呼んで処理を続ける場合は、新しい回復用レコードが作られます。

回復フックが例外を投げた場合は、レコードを残して後の起動やAlarmで再試行します。通常のコールバック実行時の例外とは扱いが異なります。回復の再試行には最大5分の指数バックオフがあり、回復用レコードの経過時間が`fiberRecoveryMaxAgeMs`（デフォルト24時間）を超えると破棄されます。^[回復フックの再試行と保持期限が説明されています [Recovery](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#recovery)]

## startFiberによるマネージドFiber

`runFiber()`は、戻り値を`await`で待つ呼び出しにも、完了を待たない呼び出しにも使えます。ただし、実行中にDOがevictionされると、回復後の結果を元の呼び出し元へ返すことはできません。^[インライン実行とfire-and-forgetの両方に対応することが説明されています [Inline vs fire-and-forget](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#inline-vs-fire-and-forget)]

`startFiber()`は、受付記録と実行状態を保持するマネージドFiberを作成します。デフォルトでは永続的な受付の完了後に受付情報と状態を返します。^[受付、状態追跡、完了待機オプションが説明されています [startFiber](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#startfiber)]

### 基本的な実装例

Webhookの受信処理で同じキーの重複受付を抑えながらバックグラウンド処理を開始する抜粋です。`webhookId`、`threadId`、`postReply()`はアプリケーション側で用意します。

```ts:src/agent.ts
const receipt = await this.startFiber(
  "reply-to-webhook",
  async (ctx) => {
    ctx.stash({ webhookId, threadId });
    await postReply(threadId);
  },
  {
    idempotencyKey: `webhook:${webhookId}`,
    metadata: { threadId },
  },
);

if (!receipt.accepted) {
  // 指定したidempotencyKeyの処理はすでに受付済みです
}
```

### startFiberの特徴

- デフォルトではコールバック関数の完了を待たず、永続的な受付の完了後に戻ります。戻り値には`fiberId`、現在の`status`、`metadata`、`accepted`フラグなどが含まれます。`waitForCompletion: true`を指定すると終端状態まで待ちます。
- `idempotencyKey`が既存の保持レコードと一致すると、新しい仕事の受付を抑止し、`accepted: false`を返します。完了待機を指定した重複呼び出しは、可能ならメモリ内で実行中の処理に合流して待ちます。
- `inspectFiber(fiberId)`や`inspectFiberByKey(key)`で後から実行状態を取得できます。状態には`pending`、`running`、`completed`、`aborted`、`interrupted`、`error`があります。
- `cancelFiber()`は状態を`aborted`に変更し、同じisolateで実行中の場合は`ctx.signal`をabortします。コールバック側でsignalを確認するなどの対応が必要で、協調しない処理は継続する場合があります。
- コールバック関数の戻り値は永続化されません。外部へ返したい処理結果は、アプリケーション側でAgentの状態やSQLテーブルなどに保存します。

これらの受付・状態管理・キャンセルの挙動は、マネージドFiberの仕様として説明されています。^[startFiberの戻り値と協調的キャンセルが説明されています [startFiber](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#startfiber)]

`idempotencyKey`による受付の重複排除と、外部APIへの副作用の重複排除は別に設計します。例えば、`postReply()`が成功した直後に中断し、回復処理でも同じ投稿を行うと、投稿が重複する場合があります。投稿先が対応する冪等性キーや、投稿済みかを照会する処理を回復手順に組み込みます。

### マネージドFiberの回復と保持

途中でevictionされると、保持レコードは`interrupted`となり、`onFiberRecovered()`へ最後のスナップショットが渡されます。回復フックから`FiberRecoveryResult`を返すと、回復後の状態を記録できます。`undefined`を返した場合は`interrupted`のままで、例外を投げた場合も`interrupted`として回復エラーを記録します。後からアプリケーション側で回復した場合は、`resolveFiber()`で状態を更新できます。^[マネージドFiberの回復結果とresolveFiberの対象状態が説明されています [startFiber](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#startfiber)]

保持レコードは`deleteFibers()`で削除できます。デフォルトの削除対象は`completed`、`error`、`aborted`で、`interrupted`は明示的に指定しない限り残ります。重複排除に使うレコードを削除した後は、そのキーに基づく以前の受付の判定もできなくなります。^[保持レコードの削除対象とキーによる既存レコードの照合が説明されています [startFiber](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#startfiber)]

## AIChatAgentやThinkでのFiberの利用例

Cloudflare Agents SDKが提供する上位フレームワーク（`AIChatAgent`や`Think`）においても、Fiberは内部基盤として使用されています。^[チャットターンにおけるFiberの活用と切断時の回復フックが説明されています [Chat recovery](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#chat-recovery)]

### チャットターンの保護

`AIChatAgent`や`Think`では、ユーザーとエージェント間の各チャットターンが内部的にFiberで包まれて実行されます。

- ユーザーからのメッセージ受信時に自動的にFiberが開始されます。
- LLMへのリクエスト送信やツール実行の途中でDOがevictionされた場合、DO再起動時にフレームワーク内部の回復ロジックが動作します。
- 必要に応じて`onChatRecovery`フックを定義することで、プロバイダーに応じた再開やユーザーへのエラーメッセージ返信などの回復方針をカスタマイズできます。

### Resumable Streamingとの関係

チャットエージェントにおける切断への対策には、2つのレイヤーが存在します。^[クライアント切断への再接続機構であるResumable Streamingの仕様が説明されています [Resumable Streaming](https://github.com/cloudflare/agents/blob/main/docs/agents/resumable-streaming.md)]

- ブラウザやクライアントのネットワーク切断に対しては、Resumable Streamingが使用されます。チャンクをSQLiteへ保存し、クライアントの再接続時に保存済みチャンクを再送します。クライアントが切断しても、サーバー側の生成は継続できます。
- DO自体のevictionやランタイム再起動に対しては、Fiberが使用されます。SQLiteに保存されたスナップショットをもとに、次回のDO起動時に`onChatRecovery`や`onFiberRecovered`経由で状態の復旧を行います。

## まとめ

Fiberは、Durable Objectsにおける処理の中断に対処するための実行管理プリミティブです。

- 非アクティブタイムアウトによる中断を防ぎたい場合は、keepAliveによるheartbeatを利用します。
- 処理の中断時に途中状態から復旧させたい場合は、runFiberと`ctx.stash`を用いてSQLiteへチェックポイントを保存し、`onFiberRecovered`で復帰方針を実装します。
- Webhook受付などのバックグラウンド処理や重複排除を行いたい場合は、startFiberと`idempotencyKey`を利用します。
- `AIChatAgent`や`Think`などのチャット機能においても、チャットターンの保護と回復の基盤として内部的にFiberが活用されています。
