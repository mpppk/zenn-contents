Cloudflare Agents SDKでは、AgentがCloudflare Durable Objects（以下DO）上で動作します。DOはメモリとSQLiteストレージを持つステートフルな実行環境です。DOはアイドル時や基盤側の再起動によって処理が中断される可能性があります。^[アイドル時の状態遷移とデプロイ・ランタイム更新時の停止動作が説明されています [Lifecycle of a Durable Object](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)]

このような処理の中断に対して、処理の継続や状態の回復を制御する仕組みとして提供されているのがFiberです。^[Agentの処理をDurable Object上で実行し状態を永続化するFiberの仕様が説明されています [Durable execution with fibers](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/)]

この記事では、DOにおける処理の中断要因、中断を抑止するkeepAlive、状態を記録して回復するrunFiberおよびstartFiberの仕組み、チャットエージェントにおける利用例について整理します。

## 学習パス
FiberはDO上に構築されているため、先にDOの仕組みについて理解しておくとスムーズです。[Cloudflare Durable Objectsの概要](https://zenn.dev/niboshi/articles/9a9769410a26d8)をご覧ください。

## Fiberとは

Cloudflare Agents SDKにおけるFiberは、DO上で実行される処理の中断に対応し、途中状態の記録や再開可能な処理を定義・制御するための仕組みです。

Fiberは新しいインフラストラクチャや実行ランタイムなどではなく、DOが標準で提供しているSQLiteストレージやAlarmといった既存のプリミティブを基盤とした抽象レイヤーです。^[FiberがDurable ObjectsのストレージとAlarmを基盤にして構築されていることが説明されています [Durable execution with fibers](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/)]

このFiberでは、SQLiteに保存したスナップショットをもとに回復処理へ制御を引き継ぎます。逆に言えばスナップショット以外(実行中の関数のクロージャ、呼び出しスタックなど)は保存されません。^[元のコールバックは失われ、回復フックで再開手順を実装することが説明されています [Recovery](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#recovery)]

## DOの処理の中断が起きる要因

Cloudflare Agents SDKのAgentはDOを基盤としています。DOは常時稼働し続ける仮想マシンではなく、リクエストを処理していない期間はリソース効率化のために停止します(Inactive化)。また、インフラストラクチャの保守や設定変更によっても停止が発生します。

Agent実装では、LLM APIからのレスポンスを長時間ストリーミングするため、リクエストを処理しない時間が多く、この影響を受けやすいのですが、長時間実行を想定したAgentでは処理が中断されると最初からやり直しになってしまい、致命的な問題となります。
Fiberはこの問題に対して以下の2つのアプローチを提供します。

- keepAliveを呼び出してハートビートを送信し、Inactive化によるevictionを防止
- runFiberまたはstartFiberを使用して処理の途中状態をSQLiteに保存し、evictionが発生した場合でも回復処理を呼び出して再開

## keepAliveによる中断の防止

keepAliveは、Inactive化によるDOの停止を防ぐためのAPIです。^[30秒間隔のheartbeatでInactive化を防ぐkeepAliveの仕様が説明されています [keepAlive](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#keepalive)]

### 基本的な使い方

非同期処理の実行前に`this.keepAlive()`を呼び出してdisposer関数を取得し、処理の完了後に呼び出します。

```ts:src/agent.ts
const dispose = await this.keepAlive();
try {
  await longWork();
} finally {
  dispose();
}
```

一定の関数スコープ内でのみ有効化したい場合は、ヘルパーメソッドである`keepAliveWhile`を利用することも可能です。

```ts:src/agent.ts
await this.keepAliveWhile(async () => {
  await longWork();
});
```

### 内部動作と注意点

`keepAlive()`を実行すると、内部でDOのAlarmを利用して、デフォルトで30秒間隔のheartbeatを生成します。間隔は`keepAliveIntervalMs`で変更できます。すべてのdisposerが呼ばれるとheartbeatが停止します。^[設定可能な間隔と参照カウントによるheartbeatの維持が説明されています [keepAlive](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#keepalive)]

keepAliveで防ぐことができるのはInactive化のみです。コードの再デプロイ、ランタイムの再起動、Alarmハンドラの15分タイムアウトなどによる中断を防ぐことはできません。また、evictionが発生した場合の回復機構も備えていません。そのため、途中状態の保持や中断後の復旧が必要な処理には、後述のrunFiberやstartFiberを使用します。

## runFiberによる状態記録と復旧

runFiberは、処理の進行状況をチェックポイントとしてSQLiteに保存しながら実行し、evictionが発生した際に回復フックを呼び出すAPIです。^[runFiberの実行モデルとチェックポイント保存の仕様が説明されています [Durable execution with fibers](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/)]

### 基本的な実装例

runFiberと回復用フックである`onFiberRecovered`を実装したAgentの抜粋です。`expensiveOperation()`と`anotherExpensiveOperation()`はアプリケーション側で定義する処理で、ここでは実装を省略しています。

```ts:src/agent.ts
import { Agent } from "agents";
import type { FiberRecoveryContext } from "agents";

export class ResearchAgent extends Agent {
  async doWork() {
    await this.runFiber("my-task", async (ctx) => {
      const step1 = await expensiveOperation();
      ctx.stash({ step1 });

      const step2 = await anotherExpensiveOperation(step1);
      this.setState({ ...this.state, result: step2 });
    });
  }

  async onFiberRecovered(ctx: FiberRecoveryContext) {
    if (ctx.name !== "my-task") return;

    const snapshot = ctx.snapshot as { step1: unknown } | null;
    if (snapshot) {
      const step2 = await anotherExpensiveOperation(snapshot.step1);
      this.setState({ ...this.state, result: step2 });
    }
  }
}
```

### 実装のポイント

* runFiberの内部でkeepAliveが自動的に呼び出され、渡した関数の実行が完了するまでタイムアウトによるInactive化を防ぎます
* DOがInactive化した場合、Agent classは自動的にDOを再起動します。その際、onFiberRecoveredが呼び出されます。onFiberRecoveredには最後にstashした内容がsnapshotとして与えられるので、これを元に処理を継続します。stashした内容はDOに紐づくSQLiteに永続化されています。
* 複数のFiberが存在する場合でも同じonFiberRecovered関数が呼び出されるため、必要に応じてctx.nameでどのFiberがrecoverされたのかを確認し、処理を分岐させてください。
* runFiberに渡した関数の戻り値を、runFiberの戻り値として呼び出し元は受け取ることができます。ただし、Fiberが戻り値を返す前にInactive化した場合、呼び出し元の残りの処理は実行されません。

## startFiberによるマネージドFiber

`startFiber()`は、受付記録と実行状態を保持するマネージドFiberを作成します。デフォルトでは永続的な受付の完了後に受付情報と状態を返します。^[受付、状態追跡、完了待機オプションが説明されています [startFiber](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#startfiber)]

### 基本的な実装例

Webhookの受信処理で同じキーの重複受付を抑えながらバックグラウンド処理を開始する抜粋です。`webhookId`、`threadId`、`postReply()`はアプリケーション側で用意します。

```ts:src/agent.ts
const receipt = await this.startFiber(
  "reply-to-webhook",
  async (ctx) => {
    ctx.stash({ webhookId, threadId });
    await postReply(threadId);
  },
  {
    idempotencyKey: `webhook:${webhookId}`,
    metadata: { threadId },
  },
);

if (!receipt.accepted) {
  // 指定したidempotencyKeyの処理はすでに受付済みです
}
```

### startFiberの特徴

- デフォルトではコールバック関数の完了を待たず、fiberの実行状況だけを返します。この挙動は`waitForCompletion`フラグで変更可能です。
- 同一の`idempotencyKey`で複数回呼び出した場合、2回目以降は実行されず、`accepted: false`を返します。
- `inspectFiber(fiberId)`や`inspectFiberByKey(key)`で後から実行状態を取得できます。
- `cancelFiber()`は状態を`aborted`に変更し、同じisolateで実行中の場合は`ctx.signal`をabortします。コールバック側でsignalを確認するなどの対応が必要で、協調しない処理は継続する場合があります。
- コールバック関数の戻り値は永続化されません。外部へ返したい処理結果は、アプリケーション側でAgentの状態やSQLテーブルなどに保存します。^[startFiberの戻り値と協調的キャンセルが説明されています [startFiber](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#startfiber)]

#### マネージドFiberの回復と保持

```ts
async onFiberRecovered(ctx: FiberRecoveryContext) {
	if (ctx.name !== "reply-to-webhook") return;

	const snapshot = ctx.snapshot as { webhookId: string; threadId: string };
	await postRecoveryMessage(snapshot.threadId);

	return {
		status: "completed",
		snapshot: { ...snapshot, recovered: true },
	};
}
```

* fiberが実行中にInactive化すると、状態が`interrupted`へ変更され、`onFiberRecovered()`が呼び出されます。
* `onFiberRecovered`から`FiberRecoveryResult`を返すと、回復後の状態を記録できます。`undefined`を返した場合は`interrupted`のままで、例外を投げた場合も`interrupted`として回復エラーを記録します。
  * 後からアプリケーション側で回復した場合は、`resolveFiber()`で状態を更新できます。^[マネージドFiberの回復結果とresolveFiberの対象状態が説明されています [startFiber](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#startfiber)]

## AIChatAgentやThinkでのFiberの利用例

Cloudflare Agents SDKが提供する上位フレームワーク（`AIChatAgent`や`Think`）においても、Fiberは内部基盤として使用されています。^[チャットターンにおけるFiberの活用と切断時の回復フックが説明されています [Chat recovery](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/#chat-recovery)]

### チャットターンの保護

`AIChatAgent`や`Think`では、ユーザーとエージェント間の各チャットターンが内部的にFiberで包まれて実行されます。

- ユーザーからのメッセージ受信時に自動的にFiberが開始されます。
- LLMへのリクエスト送信やツール実行の途中でDOがInactive化した場合、DO再起動時にフレームワーク内部の回復ロジックが動作します。
- 必要に応じて`onChatRecovery`フックを定義することで、プロバイダーに応じた再開やユーザーへのエラーメッセージ返信などの回復方針をカスタマイズできます。

### Resumable Streamingとの関係

チャットエージェントにおける切断への対策には、2つのレイヤーが存在します。^[クライアント切断への再接続機構であるResumable Streamingの仕様が説明されています [Resumable Streaming](https://github.com/cloudflare/agents/blob/main/docs/agents/resumable-streaming.md)]

- ブラウザやクライアントのネットワーク切断に対しては、Resumable Streamingが使用されます。チャンクをSQLiteへ保存し、クライアントの再接続時に保存済みチャンクを再送します。クライアントが切断しても、サーバー側の生成は継続できます。
- DO自体のevictionやランタイム再起動に対しては、Fiberが使用されます。SQLiteに保存されたスナップショットをもとに、次回のDO起動時に`onChatRecovery`や`onFiberRecovered`経由で状態の復旧を行います。
