# Sierra Agent Studioの仕様を公開情報から想像する

Sierraはチャットや音声、メールなどで顧客対応を行うAIエージェントを構築、テスト、運用するためのプラットフォームです。2024年2月の提供開始から7四半期後の2025年11月にARR 1億ドルに到達し※1、2026年2月にはARR 1億5000万ドルを超えています※2。

筆者はSierraを契約しておらず、実際の管理コンソールを操作できないため、公開されている製品ページやブログから仕様を想像します。以下では可能な限り公式情報を参照しますが、推測が含まれている点に留意してください。

## Journeys

Sierraでは、カスタマーサポートにおける応対シナリオごとの対応手順を自然言語で記述し、エージェントを構築できます。この記述内容およびその単位をJourneyと呼びます※3。

逐次的なワークフローや標準作業手順書の羅列を超えて、目標の理解やポリシーの遵守、ツールの使用、推論を組み合わせるものと説明されています※4。

記述した手順には、ナレッジの参照や外部APIの呼び出し、顧客からの情報収集などのステップを含めることができます※3。

例えば、不審な請求に対する異議申し立てを扱うJourneyでは、顧客の認証や取引データの取得、不正利用チェックなどのツール呼び出しを含む手順が自然言語で記述されています。エージェントは会話の流れに応じてそれらのアクションを実行します。

## Integration Library

外部システムとの連携を行う機能として、Integration Libraryが提供されています※4。

ナレッジベースやシステムオブレコード、コンタクトセンター向けに、事前に定義された40以上のインテグレーションが用意されています※4。

これらに加えて、ライブラリから選択して認証情報とエンドポイントを追加し、公開することで、独自の基幹システムに接続するカスタムインテグレーションも追加できます※4。

接続されたインテグレーションはツールとしてAgent StudioとAgent SDKの両方に公開され、Journey内から呼び出すことができます※4。この点は、IntercomのFinにおけるData Connectorと類似した位置づけと考えられます。

## Workspaces

複数のチームが並行してエージェントの開発や改修を進めるための仕組みとして、Workspacesが提供されています※5。

複数のチームが独立したワークスペース上で、JourneysやSimulations、ツール、設定、ナレッジ、コードを変更できます※5。

各チームによる変更はマージするまでワークスペース内に閉じた形で管理され、他のチームに影響を与えることなく独立して検証を行えます※5。

変更内容をマージする際には、同じ箇所を複数人が編集していた場合にコンフリクトが表示され、Agent Studio内で解決できます※5。マージされた更新はスナップショットとしてまとめられ、QAやステージング、本番環境へ段階的にリリースできます※5。

## Simulations

エージェントの応対品質をリリース前に検証する仕組みとして、Simulationsが提供されています※6。

言語や技術習熟度、口調の異なるモックユーザーを生成し、ログイン有無やメールアドレスの利用可否などのコンテキストを与えたうえでエージェントと対話させることで評価を行います※6。

エージェントとモックユーザーの対話ログに対して、別のエージェントがJudgeとして目標の達成可否、業務手順の遵守状況、ブランドガイドラインへの適合度、回答の正確性や有用性、分かりやすさなどを採点します※6。

テストケースは、応対手順書やナレッジベース、過去のコーチング記録、会話フローから自動的に生成できます※6。CXチーム向けにはJourneyと並べて扱い、Journey変更の公開前に合格を求める運用が可能です※6。開発者向けにはGitHub ActionsやCLIからCI/CDに接続し、リリースのゲートとして利用できます※6。

Journeyを更新した際にはテストを再実行し、応答精度の低下やデグレーションを検出します※6。

## 外部システム連携における認可制御

エージェントが外部システムへの書き込みなどの副作用を伴う操作を実行する際には、対話しているユーザーにその操作を行う権限があるかをエージェント側で確認する必要があります。

仮に外部システム側の認可制御によって不正な書き込みが最終的に防がれるとしても、副作用を持つAPI呼び出しはエージェント側で事前に防ぐ必要があります。不要なリクエストや意図しないパラメータでの呼び出し自体を抑止する必要があるためです。

従来のワークフローエンジンでは、条件を評価することでアクションを実行して良いかを判定していました。そこではIF-THEN-ELSEのような条件分岐の記述が必要になります。

Sierraでは、事前に定義されたパスに従うフローではなく、目標に導かれガードレールに制約される方式を提唱しています※7。

[https://i.gyazo.com/8951ab84c81d0822767723f68a6c42ab.jpg](https://i.gyazo.com/8951ab84c81d0822767723f68a6c42ab.jpg)
この画像は※7の記事に掲載されているアーキテクチャの対比図のキャプチャです。左側の固定的でルールベースのフローチャートに代えて、右側の目標やガードレール、ポリシーに基づく動的な方式を示しています。

ただし、Sierraにおいてワークフローという概念が完全に排除されているわけではありません。システム全体を固定的なワークフローで構築するのではなく、規制対応の受付や複数段階の確認など、厳密な手続きの順序が必要とされる特定の場面で利用する構成要素としてワークフローを扱っています※7。

Sierraのコンテキスト制御では、条件としてStateとObservationの2つを扱います※7。Stateは、ツールが特定のデータを返したことや顧客が認証済みであること、サブスクリプションが読み込まれたことなどです※7。Observationは、顧客が特定の話題に言及したことや解約の希望を示したこと、特定の製品について質問したことなどです※7。条件が満たされると、その情報がエージェントに渡されます※7。

また、ガードレールやビジネスロジックを自然言語で記述するRuleやPolicyという構成要素が存在します※7。例として、プレミアムカード保有者の海外事務手数料を免除するといった記述が挙げられています※7。このRuleやPolicyがLLMの推論にどのように強制されるかについて、公開情報では詳細は説明されていません。

公開情報ではこれ以上の具体的な認可アーキテクチャは説明されていませんが、以上の仕様から次のような仕組みになっていると考えられます。

まず、Policyにはシステム的な強制力がないため、特定の条件下でのみ呼び出しを許可すべきツールの制御には使えません。

代わりに、各ツールに対して、そのツールを利用可能にするための事前条件（pre-condition）が定義できる構成になっていると考えられます。この事前条件は、Stateやツールの実行結果を属性値とした属性ベースアクセス制御（ABAC）的なポリシーとして表現されます。

そして、この事前条件の属性値にはObservationを利用できない制約が課されていると考えられます。Stateやツールの実行結果はシステム側で保証された信頼できる情報であるのに対して、Observationはユーザーの発言内容であり、なりすましや虚偽の申告が含まれる可能性を排除できないためです。
