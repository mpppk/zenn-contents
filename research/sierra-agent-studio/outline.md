- 前提
  - 契約しておらず実際のダッシュボードは触れないので、画面は公開されているLPやブログを参照している
  - 機能についても公開情報から推測で記載しているものが多いので、実際の挙動とは異なっている可能性がある点に留意して読んでほしい
- Journeys
  - Sierraでは応対シナリオ(ジャーニー)ごとの対応手順を自然言語で記述することで、その通りに動作するエージェントを作成することができる。この記述内容をJourneyと呼ぶ
  - 文章中から、ナレッジの参照、外部システムへの書き込み、別Journeyの呼び出しなどのActionを呼び出せる
  - ![Journeys Transaction Dispute](https://i.gyazo.com/567bde56d2f12bfc0fc66c159184e90b.png)
- Integration Library
  - predefinedな40以上のインテグレーションが存在する
  - 加えて、エンドポイントと認証設定を行うだけでカスタムインテグレーションも簡単に追加できる
    - おそらくFinにおけるData Connectorのような機能ではないか
- Workspaces
  - 複数チームが並列にJourneysやSimulationsなどのリソースを変更することができる。それぞれの変更はチーム内に閉じた形で独立に検証ができる。本番リリース時のコンフリクトは自動で解消される
  - ![Workspaces workflow](https://i.gyazo.com/e83f885d2514cc4fc682f4907eda2602.png)
- Simulations
  - 事前定義したペルソナのユーザとエージェントを対話させ、応対品質を評価する仕組み
  - 応対手順書やナレッジ、過去の応対履歴から自動的にテストケースを追加できる
  - Journey更新時には自動的にSimulationが実行され、デグレを検出する
  - ![Simulations Card replacement](https://i.gyazo.com/32b5d0743056f033360a5678bde11753.png)
- 認可
  - 外部システムへの書き込み等を行う際には、今対話しているユーザにその権限があることを確認しなければならない
    - 仮に外部システム側の認可制御で書き込みが失敗するとしても、副作用を持つようなAPIであればそもそも呼び出し自体を行ってはならない
  - ワークフローエンジンではConditionを評価することでそのアクションを実行して良いかを判定していた。IF THEN ELSEのような制御文が必要になる。Finでは実際このような構文でアクションを制御する
  - Sierraではそれを明確に否定しており、代わりにガードレールによる制御を提唱している
    - ![](https://i.gyazo.com/8951ab84c81d0822767723f68a6c42ab.jpg)
    - と言いつつ、Sierraでもワークフローは利用可能である。全てをワークフローにするのではなく、一部の厳密な手続き順序が重要なケースでのみ利用するビルディングブロックである点が違いとのこと
  - SierraではStateとObservationの2つのconditionを持つ。Stateはtoolから返された結果やユーザの認証状況など、Observationはユーザの発言から分かったこと
  - ガードレールやビジネスロジックを自然言語できるPolicy。ただしLLMの解釈に依存するので強制力はない
  - これ以上の具体的なガードレールの説明はないが、おそらく次のような仕組みになっている
  - まず、Policyは強制力がないので、特定の条件下でのみ呼び出し可能なToolの制御には使えない
  - 代わりに、各Toolには、そのToolを利用可能にするためのpre-conditionを定義できる。pre-conditionはStateやTool Resultを属性値としたABAC的なポリシーとして表現される
  - このpre-conditionの属性値にObservationは利用できない。なぜなら、StateやTool Resultは確実に信頼できる情報であるのに対して、Observationはユーザの発言であり信頼できるとは限らないから
