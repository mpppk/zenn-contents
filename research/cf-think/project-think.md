## 概要: Project Thinkとは

- 次世代の Agents SDK として紹介されたものです。
- 長期間実行されるエージェントを構築するための新しいプリミティブセットと、それらを1つに接続するベースクラスから構成されます。
- プリミティブは単体で利用して必要なものを構築することも、Thinkベースクラスを使って迅速に開始することもできます。

## 背景: コーディングエージェントの証明したパターン

- Pi、OpenClaw、Claude Code、Codex のようなツールが、シンプルでありながら強力なアイデアを証明しました。
- LLMにファイルを読み、コードを書き、実行し、学習したことを記憶させると、汎用アシスタントのようなものが得られます。
- 用途はコード作成に留まらず、カレンダー管理、データセット分析、購入交渉、納税、ビジネスワークフロー全体の自動化などに広がっています。
- 共通パターンは、コンテキストを読み取り、理由を調べ、アクションを実行するためのコードを書き、結果を観察し、反復するというものです。
- コードは動作の普遍的な媒体として位置づけられています。

## 既存のコーディングエージェントの課題

- ノートパソコンか高価なVPSで動作するだけで、デバイス間の共有、コラボレーション、引き渡しはありません。
- アイドル中も高価で、エージェントが働いていなくても月額定額料金がかかります。チームや会社規模に拡張すると費用が膨らみます。
- 依存関係のインストール、アップデート管理、IDとシークレット設定など、管理と手動セットアップが必要です。
- 構造的な問題として、従来のアプリケーションは1つのインスタンスから多くのユーザーに配信されるのに対し、エージェントは1対1です。各エージェントは固有のインスタンスであり、1人のユーザーに仕え、1つのタスクを実行します。
- 例えとして、レストランは大量の料理提供に最適化されたメニューとキッチンを持つのに対し、エージェントは毎回異なる食材・技術・ツールを使う専属料理人に似ています。
- 1億人のナレッジワーカーがそれぞれエージェンティックアシスタントを使う場合、控えめな同時実行数でも何千万もの同時セッション容量が必要になり、コンテナごとのコストでは持続不可能であり、異なる基盤が必要とされています。

## Project Thinkが提供するプリミティブ一覧

記事の「Project Thinkの紹介」セクションで挙げられているセットは以下です。

- ファイバーによる耐久性のある実行: クラッシュからの復旧、チェックポイント作成、自動キープアライブ
- サブエージェント: 独自のSQLiteと型付けRPCを持つ分離された子エージェント
- 永続セッション: ツリー構造化メッセージ、フォーク、コンパクション、フルテキスト検索
- サンドボックス化されたコード実行: Dynamic Workers、コードモード、ランタイムnpm解決
- 実行ラダー: ワークスペース、分離、npm、ブラウザ、サンドボックス
- 自己作成型拡張機能: エージェントが実行時に独自のツールを作成する

## 長期間実行されるエージェント

- 現在のエージェントは一過性で、1つのセッションのために実行され、単一プロセスやデバイスに結びつき、その後消えてしまいます。
- 持続性のあるエージェントは、オンデマンドで起動し、中断後に作業を継続し、ローカルランタイムに依存せず状態を続けられるもので、インフラストラクチャのように見え始めます。
- Agents SDKはDurable Objectsを基盤とし、すべてのエージェントにID、永続的な状態、メッセージ認識能力を提供します。これはアクターモデルです。
- 各エージェントは独自のSQLiteデータベースを持つアドレス可能なエンティティです。ハイバネーション時の消費量はゼロです。
- HTTPリクエスト、WebSocketメッセージ、スケジュールされたアラーム、受信メールなどをきっかけにプラットフォームがエージェントを起動し、状態をロードしてイベントを引き渡します。作業後にスリープに戻ります。
- これにより経済性が変わり、パワーユーザーごとに1つの高価なエージェントではなく、顧客ごとに1つ、タスクごとに1つ、メールスレッドごとに1つのエージェントを構築できます。新規エージェント生成のわずかなコストは事実上ゼロです。

## ファイバーによる耐久性のある実行

- LLM呼び出しは30秒かかり、複数ターンのエージェントループはさらに長く実行されます。その間にデプロイ、プラットフォーム再起動、リソース制限などで実行環境が消失し得ます。
- `runFiber()`は耐久性のある関数呼び出しです。実行開始前にSQLiteに登録され、`stash()`で任意時点でチェックポイント可能で、`onFiberRecovered`で再起動時に回復できます。
- 記事では `ResearchAgent` が `runFiber("research", ...)` 内で10ステップの調査ループを回し、各ステップで `ctx.stash({ findings, step, topic })` し、`broadcast` で進捗を送る例が示されています。
- SDKはファイバー実行中、自動的にエージェントを有効にします。特別な設定は不要です。
- 分単位の作業には `keepAlive()` / `keepAliveWhile()` がアクティブ作業中の退去を防止します。
- より長い操作 (CIパイプライン、設計レビュー、動画生成) では、エージェントは作業を開始し、ジョブIDを保持し、ハイバネーションし、コールバック時に起動する形が示されています。

## Facetsを介したサブエージェント

- 単一エージェントがすべてを行うべきではなく、サブエージェントはFacetsを介して親と併置された子Durable Objectsであり、それぞれ独自の分離されたSQLiteと実行コンテキストを持ちます。
- 記事では `Orchestrator` が `subAgent(ResearchAgent, "research")` と `subAgent(ReviewAgent, "review")` を取得し、`Promise.all` で `search(task)` と `analyze(task)` を並列実行し、`synthesize` する例が示されています。
- サブエージェントはストレージレベルで分離され、データは暗黙的に共有されません。
- サブエージェントRPC遅延はランタイム実行の関数呼び出しであり、TypeScriptがコンパイル時に誤用を検出します。

## セッションAPI

- 数日・数週間にわたり稼働するエージェントにはフラットなメッセージリスト以上のものが必要であり、実験的なセッションAPIが明示的にモデル化します。Agentベースクラスで利用可能です。
- 会話はツリーとして保存され、各メッセージはparent_IDを持ちます。これによりフォーク (元のパスを失わず代替手段を探る) 、非破壊的圧縮 (古いメッセージを削除せず要約する) 、FTS5による会話履歴のフルテキスト検索が可能です。
- 記事では `SessionManager.create(this)` で `sessions` を作り、`create("main")`、`getHistory()`、`fork(session.id, messageId, "alternative-approach")` する例が示されています。
- セッションはAgentで直接利用でき、Thinkベースクラスが構築するストレージレイヤーです。

## ツール呼び出しからコード実行まで

- 従来のツール呼び出しは、モデルがツールを呼び出し、コンテキストウィンドウで結果を引き出し、別のツールを呼び出して戻す動作であり、対象領域拡大で高価かつ使い勝手が悪いものになります。100ファイルはモデル経由で100回のラウンドトリップを意味します。
- モデルはツールを呼び出すより、システムを使うためのコードを書く方が得意であり、これが `@cloudflare/codemode` の背後にあるインサイトです。一連のツール呼び出しの代わりに、LLMはタスク全体を処理する単一プログラムを書きます。
- 記事ではLLMが書いたプログラムがサンドボックス化されたDynamic Workerで動き、`tools.find({ pattern: "**/*.ts" })` で列挙し、`tools.read` で読み、`TODO` を収集して返す例が示されています。
- モデルとの100回の往復の代わりに単一プログラム実行で済み、トークンが少なく、実行が速く、結果が改善します。
- Cloudflare API MCPサーバーはこれを大規模に実証し、公開ツールは `search()` と `execute()` の2つのみで約1,000トークンを消費します。これはエンドポイントごとに単純なツールを使う場合の約117万トークンと対照的で、99.9%の削減です。

## 安全なサンドボックス: Dynamic Workers

- モデルがユーザーに代わりコードを書く前提では、そのコードの実行場所が問題になります。
- Dynamic Workersがそのサンドボックスです。数メガバイトのメモリで実行時に数ミリ秒でスピンアップされ、コンテナより約100倍速く、最大100倍メモリ効率があります。リクエストごとに新規起動し、コードスニペットを実行して破棄できます。
- 設計の重要点は能力モデルです。汎用マシンから始めて制約するのではなく、Dynamic Workersはアンビエント権限がほとんどない状態 (`globalOutbound: null`、ネットワークアクセスなし) から始まり、開発者はバインディングを通じてリソースごとに明示的に機能を付与します。

## 実行ラダー

- 能力モデルから自然に導かれる、エージェントが必要に応じ段階利用するコンピューティング環境の多様化が実行ラダーです。
- 階層0はWorkspaceで、SQLiteとR2に支えられた耐久性のある仮想ファイルシステムです。読み取り、書き込み、編集、検索、グループ化、差分を提供します。提供は `@cloudflare/shell` です。
- Tier 1はDynamic Workerで、ネットワークアクセスなしのサンドボックス化分離環境で実行されるLLM生成JavaScriptです。提供は `@cloudflare/codemode` です。
- 階層2はnpmを追加します。`@cloudflare/worker-bundler` はレジストリからパッケージを取得し、esbuildでバンドルし、結果をDynamic Workerに読み込みます。エージェントは `import { z } from "zod"` と記述して動作します。
- 階層3はCloudflare Browser Run経由のヘッドレスブラウザです。ナビゲート、クリック、抽出、スクリーンショットを行います。サービスがMCPやAPI経由でエージェント未対応の場合に有用です。
- Tier 4はツールチェーン、リポジトリ、依存関係が設定されたCloudflare Sandboxです。`git clone`、`npm test`、`cargo build` はワークスペースと双方向同期されます。
- 重要設計原則は、エージェントはTier 0単独でも有用であるべきで、各階層は付加的ということです。ユーザーは必要に応じ機能を追加できます。

## フレームワークではなくビルディングブロック

- これらのプリミティブはすべてスタンドアロンパッケージとして利用可能です。
- Dynamic Workers、`@cloudflare/codemode`、`@cloudflare/worker-bundler`、`@cloudflare/shell` (ツールを備えた永続ファイルシステム) はすべてAgentベースクラスで直接利用できます。
- 組み合わせでエージェントに作業領域、コード実行、ランタイムパッケージ解決を提供できます。

## プラットフォーム全体像

- 記事ではCloudflareでエージェントを構築する全スタックとして以下が挙げられています。
  - Dynamic Workers + `@cloudflare/codemode`
  - AI Gateway + Workers AI (または自身のモデル持ち込み)
- これらが合わさり、ローカルマシン上のAIエージェントと同じ能力のAIエージェントを誰でも構築・デプロイ・実行できる、サーバーレスで耐久性があり設計上安全なプラットフォームになるという説明です。

## Thinkベースクラス

- Thinkは独自規約を持つハーネスで、エージェントループ、メッセージ永続化、ストリーミング、ツール実行、ストリーム再開、拡張機能などチャットライフサイクル全体を処理します。エージェントの独自性に重点を置けます。
- 最小例は `Think` を継承し、`getModel()` でWorkers AIモデルを返すだけです。記事では `@cf/moonshotai/kimi-k2.5` を `createWorkersAI({ binding: this.env.AI })` 経由で返す例が示されています。
- これだけでストリーミング、パーシスタンス、中断/キャンセル、エラー処理、再開可能ストリーム、組み込みワークスペースファイルシステムを備えた作業用チャットエージェントになり、`npx wrangler deploy` でデプロイします。
- 制御強化時は注目箇所をオーバーライドします。
- 内部ではThinkは毎ターン完全なエージェントループを実行します。コンテキスト (基本指示 + ツール説明 + スキル + メモリ + 会話履歴) を組み立て、`streamText` を呼び出し、ツールコールを実行し (コンテキスト肥大防止の出力切り捨て) 、結果を追加し、モデル完了かステップ制限までループします。すべてのメッセージは各ターン処理後に残ります。

## ライフサイクルフック

- パイプライン全体を所有せず、チャットターンの各段階でフックを提供できます。
- 記事で示された順序は `beforeTurn() → streamText() → beforeToolCall() → afterToolCall() → onStepFinish() → onChatResponse()` です。
- フォローアップターンを低コストモデルに切り替え、使用ツールを制限し、ターンごとにクライアントサイドコンテキストを渡せます。
- 分析への全ツール呼び出しログ記録や、モデル完了後に `onChatMessage` 置換なくフォローアップターンを自動再トリガーできます。

## 永続的メモリと長い会話

- ThinkはセッションAPIをストレージレイヤーとして利用し、ブランチング組み込みのツリー構造メッセージを提供します。
- さらにコンテキストブロックで永続メモリを追加します。これはモデルが時間経過で読み取り・更新できるシステムプロンプトの構造化セクションで、ハイバネーション後も存続します。モデルは `MEMORY (重大な事実、更新にはset_contextを使用) [42%、462/1100トークン]` のように見て積極的に記憶できます。
- 記事では `configureSession(session)` で `withContext("soul", ...)` (読み取り専用identity的用途) と `withContext("memory", ...)` (会話で学んだ重要事実、maxTokens 2000) を定義し、`withCachedPrompt()` する例が示されています。
- エージェントごとに複数会話を実行でき、元を失わず別方向へフォークできます。
- コンテキスト拡大時は非破壊的圧縮で対応します。古いメッセージは削除されず要約されますが、全履歴はSQLiteに保存されます。
- 検索機能は組み込みで、FTS5によりセッション内または全セッションの会話履歴をクエリできます。エージェントは `search_context` ツールで自身の過去を検索できます。

## 実行ラダーの統合

- 実行ラダー全体を統合して一つの `getTools()` に返します。
- 記事の例では `createWorkspaceTools(this.workspace)` を束ねた `createExecuteTool` (loaderに `this.env.LOADER`) 、`createBrowserTools(this.env.BROWSER)`、`createSandboxTools(this.env.SANDBOX)` (エージェントごとにツールチェーン・リポジトリ・スナップショット設定) 、`createExtensionTools({ manager: this.extensionManager! })` と `this.extensionManager!.getTools()` をマージしています。

## 自己作成型拡張機能

- Thinkはコード実行をさらに進め、エージェントは独自拡張を記述できます。Dynamic Workersで実行され、ネットワークアクセスやワークスペース操作許可を宣言するTypeScriptプログラムです。
- 記事では `name: github`、`description: GitHub integration: PRs, issues, repos`、`tools: create_pr, list_issues, review_pr`、`permissions: network: [api.github.com]、workspace: read-write` の例が示されています。
- ThinkのExtensionManagerは拡張機能 (オプションで `@cloudflare/worker-bundler` 経由のnpm依存含む) をバンドルし、Dynamic Workerにロードして新ツールを登録します。
- 拡張機能はDOストレージに永続的でハイバネーションに耐えます。ユーザーが次にプルリクエストを尋ねる際、エージェントは30秒前になかった `github_create_pr` ツールを持てます。
- 微調整やRLHFではなくコードを通じた自己改善ループであり、サンドボックス化・監査可能・取り消し可能なTypeScriptで新機能を自書するという説明です。

## サブエージェントRPC

- Thinkもサブエージェントとして機能し、親からRPC経由で `chat()` で呼び出され、コールバック経由でイベントをストリーミングします。
- 記事では `subAgent(ResearchSession, "research")` で取得し、`researcher.chat(\`Research this: ${task}\`, streamRelay)` する例が示されています。
- 子はそれぞれ独自の会話ツリー、メモリ、ツール、モデルを取得します。親は詳細を知る必要はありません。

## 利用開始

- Project Thinkは実験的です。APIサーフェスは安定していますが、今後数日・数週間で進化し続けます。独自バックグラウンドエージェントインフラ構築に社内利用済みで、早期共有で共に構築できるようにしたという説明です。
- 導入は `npm install @cloudflare/think agents ai @cloudflare/shell zod workers-ai-provider` です。
- サーバー例は `Think` 継承の `MyAgent` 定義と `routeAgentRequest(request, env)` でWorker entryから振り分ける `fetch` です。不明時は404応答です。
- クライアント例は `agents/react` の `useAgent({ agent: "MyAgent" })` と `@cloudflare/ai-chat/react` の `useAgentChat({ agent })` で、`messages`、`sendMessage`、`status` を使ってチャットUIを描画します。
- Thinkは `@cloudflare/ai-chat` と同じWebSocketプロトコルを使うため、既存UIコンポーネントはすぐ動作します。AIChatAgent基盤でもクライアントコードは変更されません。

## 第3の波

- 第1の波はチャットボットで、ステートレスでリアクティブで脆弱でした。会話は毎回ゼロ開始で、メモリもツールも行動もなく、質問回答に有用だが限定されました。
- 第2の波はPi、Claude Code、OpenClaw、Codeexのようなコーディングエージェントで、ステートフルでツール使用のはるかに能力の高いものです。コードベース読み取り、コード作成、実行、反復ができ、適切ツール付きLLMは汎用マシンと証明しましたが、1ユーザー向けノートパソコン上で動作し耐久性は保証されません。
- 第3の波はインフラとしてのエージェントで、耐久性、分散性、構造的安全性、サーバーレスです。インターネット上で実行され、障害に指定され、アイドル時コストなし、動作ではなくアーキテクチャでセキュリティ強化し、開発者が任意ユーザー数向けに構築・デプロイできます。
- Agents SDKはすでに数千の本番エージェントを支え、Project Thinkと導入プリミティブで不足ピースを追加し、永続ワークスペース、サンドボックス化コード実行、耐久性ある長期実行タスク、構造的セキュリティ、サブエージェント調整、自己認証などでエージェント能力を劇的に向上させます。
- プレビューとして公開され、共に構築していくという締めです。ThinkはCloudflare Agents SDKの一部 (`@cloudflare/think`) で、説明機能はプレビュー版、フィードバックでAPI変更があり得ます。ドキュメントと例から開始できます。
